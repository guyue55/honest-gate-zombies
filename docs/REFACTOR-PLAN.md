# 重构计划：士兵/僵尸写实化 · 关卡加长 · 关卡内陷阱

> 依据用户指令（2026-11-10）：「士兵和敌人（僵尸）太假，联网充分调查清楚，然后重构优化，而且每一关时间太短，关卡内的陷阱之类的样式也太少，等于没有。注：一些问题、结论必须二次分析确认。」
> 本文先给第一遍分析，再做 **二次分析确认**（可行性 / 硬约束 / 回归风险），最终结论用于指导实现。

---

## 一、第一遍分析：问题 → 方案

### 问题 1：士兵/僵尸「太假」
- **代码证据**（`index.html`）：
  - `drawUnit`（士兵，约 1773–1809 行）：阴影椭圆 + 两根 line 腿（正弦摆动）+ 胶囊身体（渐变）+ 圆圈头 + 一条枪线。本质是「胶囊+圆头+两根棍」。
  - `drawHorde`（僵尸，约 1812–1859 行）：阴影椭圆 + 渐变胶囊身体 + 两根红色线臂 + 粉色圆头 + 命中闪白。本质是「胶囊+圆头+两根棍」。
- **结论**：两者都只有 2 个基础图元 + 棍状四肢，无真实肢体关节、无姿态、无明暗体积、无角色差异，所以「假」。
- **调研支撑**（联网）：
  - 卡通角色「去假」靠：① 部件拆分异步运动（头稳定、躯干微倾、四肢摆幅不同）[Unity 开发者社区]；② 厚描边 + 平涂/赛璐珞明暗（大块阴影、限制 4–6 色）[ cartoon zombie 指南、98uc 像素僵尸]；③ 程序化骨骼/关节角（2-bone IK）做行走循环 [wobblox IK]；④ 僵尸特征：驼背前倾、前伸爪臂、破衣、凹陷眼窝、腐绿灰肤色、暴露骨/血迹 [qyhs / bloomvara / pvz 百科]。

### 问题 2：每一关时间太短
- **代码证据**：`gateCountFor(level)=min(6, 2+floor(level/3))` → 第 1 关仅 **2 组**门；S2 时长 = `GROUP_LEAD(1400)+ (n-1)*GROUP_INTERVAL(1500)+GROUP_TAIL(780)`，第 1 关约 **3.7s**；加 PREVIEW 2s + BATTLE 1.6s ≈ **7.3s/关**。
- **结论**：组数少 + 节奏快 → 单关体感短。
- **调研支撑**：runner 完美通关建议 30s–2min [Level Design Guidelines]；但本作是「跑酷+自动战斗」单关，不宜照搬长关卡；应**适度加长**（更多门组 + 略放慢节奏），让「+1/+2 膨胀→开火」的爽点更充分，同时不拖沓。

### 问题 3：关卡内陷阱样式太少，等于没有
- **代码证据**：全仓检索 `trap|hazard` 仅命中常量/命名，运行时**无任何陷阱实体**；S2 只有门组，玩家只需对准正门，无需要躲避的 hazards。
- **结论**：用户要的是「关卡内的陷阱样式」——沿赛道分布、需用走位规避的 hazard，且要有多种**视觉样式**。
- **调研支撑**：三车道 runner 的障碍（低栏/高梁/墙/货箱）靠「提前读、选安全 lane」[Kiloo Lane Runner / inkplay]；Wurst Dash 用旋转刀/烤架/压锤等**多种陷阱类型** + 读节奏 [ohgames]；障碍设计铁律：可读、公平、不随机、失败快重来 [Level Design Guidelines]。

## 二、二次分析确认（用户硬性要求）

对第一遍结论逐条复核，确认其成立且不与既有硬约束冲突。

### 确认 1：写实化不会破坏「零外部资源 / 单文件 / 确定性」
- 士兵/僵尸仍全部 **Canvas 2D 程序化绘制**，不引入图片/精灵表 → 外链数保持 0，单文件不变。
- 动画只用 `frame`/`phase`/`index` 派生，**不引入 `Math.random`** → 确定性保留（静态审计 U-9 / core 无随机源 仍成立）。
- 性能：避免每精灵 `createLinearGradient`（90–120 个僵尸时每帧建渐变偏贵）；改用**平涂双色 + 厚描边**模拟赛璐珞，与调研 ② 一致且更省。

### 确认 2：加长关卡不破坏可解性/张力断言（最关键）
- `gateCountFor` 改为 `min(6, 3+floor(level/3))`：第 1 关 3 组。更多组 = 更多 ×2/×3 乘法门 → **最优路径兵力更大，更稳胜**；最差路径仍每组选负门 → 仍必败。
- 既有不变量（每组≥1 正门、≥1 负门、最优必胜、最差必败）**不受影响**。
- 风险点：`core.test.js` 硬编码 `gateCountFor(1)===2 / (5)===3 / (12)===6` → **必须同步改为 3 / 5 / 6**；`Object.keys(Core).length===26` 不变（仅改常量数值，不增 API）。

### 确认 3：陷阱机制如何不破坏「100% 诚实 / 每关可胜」
- 设计铁律：**陷阱只落在「非正门 lane」**（生成时跳过 positive lane）。
- 于是：最优路径总是选正门且避开陷阱 → `bestPath` 兵力不含陷阱惩罚 → `verifySolvable` 仍成立（可胜）。
- 陷阱惩罚只作用在**误走到负门 lane 的玩家** → 惩罚贪心/误判，增加「读赛道、避开危险 lane」的真实玩法，不制造不可胜关卡。
- 数值：扣兵比例 `TRAP_NUM/TRAP_DEN = 1/5`（损失 20%），用 BigInt 整数运算；新增 `CONSTANTS.TRAP_NUM/TRAP_DEN`（数据字段，非导出 API，不影响 26 项）。
- `bestPath` 与 `applyGatePath` 同时计入陷阱 → 两者一致性断言仍成立。
- 风险点：Session 的 `resolveGroup` 当前只 `applyGate`，必须补「若选中 lane 受陷阱则按 TRAP 扣兵 + trap 特效/音效」，否则视觉陷阱与实际伤害脱节（不诚实）。

### 确认 4：陷阱视觉多样且不破坏零请求/确定性
- 类型循环：`spike / saw / fire / crusher`，按 `(groupIndex*3+lane) % 4` 确定性选取 → 多样式、无随机。
- 陷阱随门组在 S2 中由远及近滚动（复用 `updateGates` 的 z 进度逻辑），在 `S.traps` 产出、buildState 透传、Renderer `drawTraps` 绘制。
- 仍零外部资源、确定性。

### 确认 5：节奏放慢不破坏浏览器自动化对齐
- 放慢 `GROUP_LEAD/INTERVAL/TAIL` 反而给 QA 对齐更宽窗口；已加固的 `align_verified`（activeGroup 主动对准 + targetX 闭环）更稳。仍会在交付前重跑 Playwright 双协议验证。

## 三、最终结论（用于实现）
1. **士兵/僵尸**：重写为带关节肢体 + 行走循环 + 赛璐珞明暗 + 多变体（士兵：头盔/护甲/持枪；僵尸：驼背前伸/破衣/凹陷眼/腐色变体）的程序化绘制，零资源、确定性、平涂省性能。
2. **加长关卡**：`gateCountFor=3+floor(level/3)` 封顶 6；S2 节奏放慢约 25–30%；同步 `core.test.js` 期望值。
3. **关卡内陷阱**：Core 生成 `traps/trapTypes`（仅非正门 lane），`bestPath/applyGatePath/resolveGroup` 计入惩罚，S2 滚动渲染 4 种陷阱样式，触发扣兵+特效。
4. 全程维持：单文件、`file://` 双击可玩、运行时 0 外链、BigInt 无限关卡、确定性、26 项 Core API 不变、100% 诚实玩法。
5. 实现后重跑 Node 三层 + Playwright 双协议 + 截图，更新 `TEST_REPORT.md`。

## 四、二次分析复核（本轮实测新发现：陷阱「等于没有」的根因与修复）

> 用户原话强调「一些问题、结论必须二次分析确认」。第一遍（上一轮）的结论「陷阱已存在」在**数据结构层面成立**，但本轮进入真实浏览器复核后，发现它在**玩家体感层面不成立**——这正是用户「等于没有」的确切含义。故在此做二次深挖与确认。

### 4.1 二次发现：第一遍陷阱实现仍「约等于无」
- **实测证据**（Playwright + 本机 Chrome，读取 `window.__GAME_CORE__.generateLevel`）：
  - 旧逻辑 `if (negLanes.length > 0 && rng() < 0.5)`：每门组仅 50% 概率放 1 个陷阱，且只落「非正门 lane」。
  - 第 1 关实测 `traps`：`[{f,f,f},{f,f},{f,f,f}]` → **0 陷阱**。
  - 即便某关有陷阱，也只落在最优路径绝不会走的负门 lane，且 S2 中该门组逼近时 z 很小（远、小、与门重叠），肉眼几乎不可辨。
- **结论再确认**：用户「陷阱样式太少，等于没有」是**真实且准确**的——不是样式种类少（已有 4 种），而是**出现频率过低 + 渲染过弱**，导致实战中基本看不到、也感知不到。第一遍「陷阱已存在」属片面结论，必须修订。

### 4.2 修复方案（二次确认不破坏硬约束）
- **频率**：改为「`rng() < 0.72` 时铺满该门组全部非正门 lane；否则至少放 1 个」，使**绝大多数门组都带陷阱**，且 1–2 个非正门 lane 同时被占 → 视觉上"错误门 = 危险"一目了然。
- **渲染**：`drawTraps` 新增**红色危险警示带 + 黑黄斜纹危险条**（始终可见，对准当前 lane 时更亮），精灵整体放大 1.25×（远距仍可见）。
- **样式多样**：`TRAP_TYPES=[spike,saw,fire,crusher]` 按 `(groupIndex*3+lane+li)%4` 循环，保证跨关 4 种全现。

### 4.3 二次确认：修复后的不变量依旧成立
- **100% 可胜（可解性）**：陷阱仍**只落非正门 lane**；`generateLevel` 经 `verifySolvable`（用 `bestPath`，已含陷阱惩罚）反复重生，并保留 `forceMultiplier` 兜底 → 每关必有正门、最优路径永远无陷阱。`bestPathAvoidsTraps` 实测 **80/80 关 = true**。
- **确定性**：频率/类型全由种子化 PRNG 与下标推导，无 `Math.random` 参与。
- **零外部资源 / 单文件 / 26 项 Core API 不变**：仅改 `buildGroups` 内陷阱生成分支与 `drawTraps` 绘制逻辑，未增删导出 API、未引外部资源。
- **回归**：`core.test.js` 11844 项全绿（陷阱不变量「只落非正门 lane / bestPath 避开 / 走陷阱 lane 终值更低」仍成立）；`extract-core` 26 项、`static-audit` 0 硬违规仍 PASS。

### 4.4 实测验收（真实浏览器）
- 陷阱样式齐现且可见：4 种类型跨 80 关计数 spike=155 / crusher=148 / saw=129 / fire=118；每关必有陷阱组（80/80），共 550 个陷阱组。
- 4 关完整通关：L1 10→120→117(含陷阱扣兵)、L2 11→297→294、L3 13→468→465、L4 15→1620→1616，全部 WIN；`ext:0`（零外链）、`CONSOLE/PAGEERR` 空。
- 截图：见 `tests/screenshots/refactor_trap_on_2.png`（尖刺+压锤近景）、`refactor_s3_zombies.png`（写实士兵开火 vs 驼背僵尸）、`refactor_win.png`。

**最终判定**：用户三项诉求（士兵/僵尸太假、关卡太短、陷阱等于没有）均已联网调研、二次分析确认、重构实现并通过真实浏览器验证。
